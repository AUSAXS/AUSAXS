# Rigid-body refinement against SAXS data

_**Notice**: This tool is still in active development._

This tool allows you to perform custom rigidbody optimizations on your structures. Here we cover all of the arguments and settings available for the procedure, and also how to write your own configuration scripts. 

_**NEW**_: You can now use this tool via the new Python GUI. Simply run the following commands to start it!
```python
pip install pyausaxs[all]
ausaxs gui
```
The [rigid-body tutorial](https://sastutorials.org/RigidBody/RigidBodyGUI.html) walks through a complete refinement in the GUI.

## Arguments
The optimization is fully described by a configuration script, which is the only required argument:  
`ausaxs rigidbody <configuration script>`

The script must have one of the extensions `.config`, `.conf`, or `.txt`. The structure and SAXS data files are loaded by the script itself, through the [`load`](#load) element. 

The remaining command-line arguments follow the same _group_ structure as the [SAXS fitter](saxs-fitter.md#argument-groups), and can be listed with `ausaxs rigidbody --help`: 
| Group       | Arguments |
|-------------|-----------|
| base        | `--licence`, `-v`/`--version`, `--allow-unknown-atoms`, `--allow-unknown-residues`, `--offline`, `-t`/`--threads`, `--gpu` |
| `config`    | `-f`/`--file`, `--save`, `--log` |
| `data`      | `--qmin`, `--qmax`, `-u`/`--unit`, `--skip`, `--rebin`, `--weighted-bins` |
| `molecule`  | `--use-occupancy`/`--ignore-occupancy` |
| `hydrogens` | `--keep`/`--discard` |
| `grid`      | `-w`/`--width` |

These work exactly as described for the SAXS fitter. Note that, unlike the fitter, a settings file is only used if it is given explicitly with `config --file`. Settings can also be changed from within the script with the `settings` element (see [advanced elements](#advanced-elements)). 

### Output
By default all output will be saved in the `output/rigidbody/` folder. This location can be changed with the [`output`](#output) element of the script. 

Only the files requested by the [`save`](#save) elements of the script are written, so remember to save at least the final structure!

## Configuration scripts
Due to the modular nature of our optimization algorithm, you can specify your very own custom routine. The rest of this page covers all options for this feature. 

### Syntax
A script consists of a sequence of _elements_, one per line. Everything after a `#` is a comment. Arguments can be given in one of two forms: 
* _Inline_: written on the same line as the element, e.g. `seed 42`. Values containing spaces must be quoted, e.g. `print "Hello world"`. 
* _Block_: written over multiple lines, one named argument per line, enclosed in braces: 
  ```
  load {
      pdb data/structure.pdb
      saxs data/measurement.dat
  }
  ```

The two forms cannot be combined; an element takes its arguments either inline or in a block, never both. Unrecognised argument names and wrong argument counts are both rejected, with the error listing what the element accepts. Lists of values can be separated by either spaces or commas. 

#### Scopes
A few elements ([`loop`](#loop), [`optimize_once`](#optimize_once), [`on_improvement`](#on_improvement), and [`every`](#every)) open a _scope_: a block of elements they control, which must be closed by an explicit [`end`](#end) statement. Scopes can be nested in any way you like. 

<details markdown="1">
<summary>Example of scopes</summary>

```
loop 100
  optimize_once
    on_improvement
      # this will be printed on every improvement
      print "Iteration {iteration} accepted. New best chi2: {chi2_best}"
    end
  end
  every 5
    # save the current state every 5 iterations
    save trajectory.xyz
  end
  loop 10
    # this will run a total of 1000 times
  end
end
```
</details>

#### Body names
Most elements refer to bodies by name. Bodies are given the default names `b1`, `b2`, ... in the order they are loaded, and can be given custom names through the [`load`](#load) element or the `rename` element. The default name always remains valid, even after a body is renamed. 

The copies generated by a [symmetry](#symmetry) are named after the body they belong to: `b1s1` is the first symmetry of body `b1`, and `b1s1r2` is the second copy (replica) generated by that symmetry. `b1s1` is shorthand for `b1s1r1`. Use `print {body_names}` to list all available names. 

### Example configurations
A script typically consists of four parts: 
1. Load the structure through the `load` element, and possibly split it into bodies. 
2. Restrain the structure, either through manual `constrain` elements or the automatic `autoconstrain`. 
3. Specify how the structure is transformed: the `parameters` element generates the transformation parameters, while the optional `select` and `transform` elements choose which body to transform, and _how_ it is transformed. 
4. Run the optimization with a `loop` element enclosing an `optimize_once` element. Optionally, you can add some `on_improvement` and `print` elements to get an insight into the optimization process. 

Some examples are given below. 
<details markdown="1">
<summary>Single-chain structure optimization</summary>

```
output output/single_chain
load {
	pdb data/structure.pdb
	saxs data/measurement.dat
	split 7 99 199 292
}
autoconstrain backbone

save initial_state.pdb
save trajectory.xyz
parameters {
	iterations 1000
	translate 10
	rotate 0.5
}

print "Initial chi2: {chi2}"
loop
	optimize_once
		on_improvement 
			print {
				msg "{iteration}/{iterations_total}: Accepted with new chi2 {chi2}"
				colour green
			}
			save curve_%.fit
			save trajectory.xyz
		end
	end
end
save final_state.pdb
```
</details>


<details markdown="1">
<summary>p2 symmetry</summary>

```
load {
	pdb data/monomer.pdb
	saxs data/dimer.dat
}
symmetry p2
constrain {
	first b1s1
	second b1
	type attract
	distance 30
}
output output/symmetry

save initial_state.pdb
save trajectory.xyz
parameters {
	iterations 1000
	sym_translate 20
	sym_rotate 1.5
}

loop
	optimize_once
		save full.xyz
		on_improvement 
			print {
				msg "{iteration}/{iterations_total}: Accepted with new chi2 {chi2_no_penalty}"
				colour green
			}
			save trajectory.xyz
		end
	end
end
save final_state.pdb
```
</details>

### Essential elements

#### load
_`load { pdb <paths>, saxs <path>, split <splits>, names <names> }`_  

* **`pdb`** [`string`, `vector<string>`]: Path to the structure file(s). 
* **`saxs`** [`string`]: Path to the SAXS data file. 
* `split` [`string`, `vector<int>`]: Declare how to split the structure file into bodies. 
* `names` [`vector<string>`]: Custom names for the loaded bodies. 

This element handles all external file imports and thus supports a few different modes. It only accepts the block form. 

_Single file_: 
- If `pdb` is a single path and no `split` is given, the entire structure is loaded as a single body. 
- If `pdb` is a single path and `split chain`, the structure is split into multiple bodies based on their chainID. 
- If `pdb` is a single path and `split` is a list of residue ids, the structure is split into multiple bodies at these ids. 

_Wildcards_: 
* If `pdb` is a single path containing the character `%`, it is interpreted as a wildcard. Each `%` is one digit of zero-padding.  
_Example_: Say you want to load the three files `file01.pdb`, `file02.pdb`, and `file03.pdb`. Then you can use `pdb file%%.pdb` to load them all.

_Multiple files_: 
* If `pdb` is a list of paths, each structure is loaded as a separate body. 

If the `names` argument is supplied, it must contain exactly one name per loaded body. See [body names](#body-names). 

<details markdown="1">
<summary>Example</summary>

Three alternative ways of loading a structure:
```
# one structure, split at residues 50 and 120 into three bodies with custom names
load {
	pdb structure.pdb
	saxs measurement.dat
	split 50 120
	names nterm core cterm
}
```
```
# one body per chain
load {
	pdb complex.pdb
	saxs measurement.dat
	split chain
}
```
```
# one body per file
load {
	pdb domain1.pdb domain2.pdb
	saxs measurement.dat
}
```

</details>

> [!TIP]
> Structure paths are resolved relative to where the program was launched, and then relative to the folder holding the configuration script. The latter lets a script reference structures placed next to it no matter where it is run from.

#### output
_`output <path>`_ or _`output { path <path>, mode <mode> }`_  

Set the folder all output is written to. 

* **`path`** [`string`]: The output folder. 
* `mode` [`string`]: How `path` is resolved.  
  i. `relative`: Relative to where the program was launched. This is the default.  
  ii. `relative_config`: Relative to the folder holding the configuration script. 
  iii. `absolute`: As an absolute path.

> [!IMPORTANT]
> The paths of [`save`](#save) elements are fixed when they are read, so this element must come _before_ any `save` element it should apply to.

#### parameters
_`parameters { iterations <N>, translate <x>, rotate <x>, translate_axes <axes>, rotate_axes <axes>, sym_translate <x>, sym_rotate <x>, decay <strategy> }`_

Specify a parameter generator for the transformations. This element only accepts the block form. 
* **`iterations`** [`int`]: The number of iterations the amplitudes decay over. This is also the default iteration count of a following [`loop`](#loop). 
* `translate` [`float`]: the amplitude of body translations, in Ångström.
* `rotate` [`float`]: the amplitude of body rotations, in radians.
* `translate_axes` [`string`]: restrict body translations to the given axes, e.g. `xy` or `z`. Requires a non-zero `translate`. 
* `rotate_axes` [`string`]: restrict body rotations to the given axes. Requires a non-zero `rotate`. 
* `sym_translate` [`float`]: the amplitude of symmetry translations, in Ångström.
* `sym_rotate` [`float`]: the amplitude of symmetry rotations, in radians.
* `decay` [`string`]: `linear`, `exponential`, `none`. Defaults to `linear`.

Each amplitude is an upper bound on the magnitude of that component's contribution to a single step, scaled down over the run by the `decay` strategy. The four components are independent, and are disabled by leaving them out or setting them to zero. At least one must be given, except when the structure has [declared symmetries](#symmetry): the symmetry amplitudes are then set to sensible defaults.

* `translate` and `rotate` move the real bodies themselves.
* `sym_translate` and `sym_rotate` move the parameters of any [declared symmetries](#symmetry).

The axes are those of the frame the structure was loaded in. 

<details markdown="1">
<summary>Which amplitudes should I set?</summary>

For a structure of independent bodies joined by constraints, use `translate` and `rotate`.

For a structure whose only freedom is a declared symmetry, use `sym_translate` and `sym_rotate` only. The symmetric copies are generated from the base body's _current_ position, so translating or rotating the base body moves the whole assembly rigidly and does not change the scattering — spending steps on it is pure waste.

For a structure with both (e.g. a symmetric assembly whose subunit has been split into domains), set all four. Their relative sizes then express how much you trust each part of the starting model.
</details>

> [!TIP]
> A good strategy is to start with big transforms and perfect the structure at the end. Note that the amplitudes decay over the run, so an over-large starting amplitude is not fatal — it merely wastes the early iterations, during which nothing is accepted. If your run only starts improving halfway through, your amplitudes were too large.

> [!NOTE]
> All rotation amplitudes are angles in radians. `rotate 3` is thus a rotation of nearly 172°, not 3°.

#### loop 
_`loop <name> <N>`_ or _`loop copy <name>`_  

Open and loop over a new [scope](#scopes) `N` times.

* `name` [`string`]: The name to reference this loop by later.  
* `N` [`int`]: The number of times the scope will be run. 

Both arguments are optional. If `N` is not provided, the `iterations` number from the nearest preceding [`parameters`](#parameters) element will be used instead; it is an error if there is none. 
Remember to terminate the scope with an `end` statement.  

_Copying a loop_:  
`loop copy <name>` runs the named loop again, exactly as it was defined, including all of its contents and its number of iterations. If `name` is left out, the most recently named loop is copied. `loop duplicate` is an alias. 
A copy does _not_ open a new scope, and should _not_ be terminated by an `end` statement. 

<details markdown="1">
<summary>Example</summary>

```
loop coarse 500
	optimize_once
	end
end

parameters {
	iterations 200
	rotate 0.1
}
loop refine      # 200 iterations, taken from the parameters above
	optimize_once
	end
end

loop copy coarse # run the 500 coarse iterations once more
```
</details>

> [!TIP]
> This is very useful for longer scripts which alternate between a few different stages, as each stage only has to be written once. 

---

#### optimize_once
_`optimize_once`_  

Generate and apply a single transform using the current set of parameters. `optimize_step` is an alias of this element. 
This will open a new [scope](#scopes) containing the transformed structure. When the scope ends, the structure fitness is evaluated:
* $\chi^2$ is better than the current best: The transformed structure is kept, and will persist after the scope ends. 
* $\chi^2$ is worse: The transformed structure will be discarded when the scope ends. 

Remember to terminate the scope with an `end` statement. 
> [!NOTE]
> This is the main element of your script. Every time this element is activated, one optimization step is run. You essentially always want this inside a `loop` element. 

---

#### end
_`end`_  

Mark the end of a [scope](#scopes).

#### save
_`save <path>`_  

Save the current conformation.  
* **`path`** [`string`]: The path to write to, relative to the [output folder](#output). The extension defines the saved data:  
  i. `*.pdb`: Save the current structure in the `pdb` format.  
  ii. `*.xyz`: Append the current structure to the specified file. This is an animation format which can be played in PyMOL.  
  iii. `*.fit`: Save the current fit, in the same format as the `ausaxs.fit` file from the [SAXS fitter](saxs-fitter.md#output).  
  iv. `*.txt`: Save a report of the current fit.  
  v. `*.png`: Save a plot of the current fit. This is written as a `.plot` file; see [CLI plotting](plotting-scripts.md). 

You can use a wildcard `%` in the path name to avoid overwriting the same data file: `out_%.pdb` creates the file `out_1.pdb` on first activation, `out_2.pdb` on second activation, and so on. Each path has its own counter.

### Common elements

#### constrain
_`constrain { first <body>, second <body>, type <type>, iatom1 <index>, iatom2 <index>, distance <distance> }`_  

Create constraints between bodies. 
* **`first`** [`string`]: The name of the first body.
* **`second`** [`string`]: The name of the second body.
* **`type`** [`string`]: Declare the type of constraint. 
* `iatom1` [`int`]: The index of the first atom. 
* `iatom2` [`int`]: The index of the second atom. 
* `distance` [`float`]: The target distance in Ångström. 

The following options are available for the `type`:
 1. `bond`: Constrain the backbone bond between the two bodies. The C-alpha pair is chosen automatically among the terminal residues of each body. Takes no further arguments.  
 2. `cm`: Keep the center-of-mass distance of the two bodies at its current value. Takes no further arguments.  
 3. `distance`: Keep the distance between atom `iatom1` of the first body and atom `iatom2` of the second body at its current value. Both atoms must be carbon atoms.  
 4. `attract`: Penalize center-of-mass distances larger than `distance`.
 5. `repel`: Penalize center-of-mass distances smaller than `distance`.

`first` and `second` accept any [body name](#body-names), including those of symmetry copies. `iatom1` and `iatom2` are the positions of the atoms within their bodies, counted from zero in file order.  

<details markdown="1">
<summary>Example</summary>

One constraint of each type:
```
constrain {
	first b1
	second b2
	type bond
}
constrain {
	first b2
	second b3
	type cm
}
constrain {
	first b1
	second b3
	type distance
	iatom1 13
	iatom2 40
}
# keep the symmetry copy within 30 Å of its base body
constrain {
	first b1
	second b1s1
	type attract
	distance 30
}
# but no closer than 15 Å
constrain {
	first b1
	second b1s1
	type repel
	distance 15
}
```

</details>

> [!NOTE]
> You can chain any number of constraint elements to constrain your system just the way you want!

#### autoconstrain
_`autoconstrain <strategy>`_  

Automatically create constraints between all bodies.  
* **`strategy`** [`string`] sets the generation strategy.  
  i. `backbone`: Go through the endpoints of each pair of bodies. If the C-alpha atoms located at these endpoints are close, create a `bond` constraint between them.  
  ii. `none`: Do not generate any constraints.  

> [!TIP]
> This element is useful for quickly linking the backbone of a split single-chain structure.

#### symmetry
_`symmetry <bodies> <symmetry group>`_

* **`symmetry group`** [`string`]: The symmetry group to instantiate. Options:  
  i. `p2`: Point group of order 2. Ideal for dimers.  
  ii. `c[2-12]`: Cyclic group of order [2-12].  
  iii. `tetrahedral`, `octahedral`, `icosahedral` (or `t`, `o`, `i`): Various polyhedral symmetries.  
  iv. `d[2-12]`: Dihedral group of order [2-12]. 
  v. `dp[2-12]`: Planar dihedral group of order [2-12]. 
  vi. `<inner>-<outer>`: A composite of two symmetries, e.g. `c3-p2`, where the copies generated by `inner` are themselves replicated by `outer`. 
* `bodies` [`string`]: The body to attach the symmetry to. This can only be left out if there is just a single body.  

Declare a symmetry for a given body. Repeat the element to declare symmetries on several bodies. 

If two or more bodies are given, they share a single symmetry, which replicates the group as one rigid assembly. Only point, cyclic, and polyhedral symmetries (and composites of these) are supported in this case. 

<details markdown="1">
<summary>Example</summary>

```
# a trimer of b1
symmetry b1 c3

# a dimer of the b2-b3 pair, where the copy of b2 and b3 move together as one unit
symmetry b2 b3 p2

# a dimer of trimers of b4
symmetry b4 c3-p2
```

</details>

<details markdown="1">
<summary>Why should I declare symmetries instead of simply optimizing two copies of the same domain?</summary>  
By declaring a symmetry with this element, you switch to a more efficient symmetry-aware distance calculator.  
You also restrain the system to have fewer optimizable parameters over the two-copy approach, further increasing efficiency. 
</details>

#### convert_to_symmetry
_`convert_to_symmetry <type>`_ or _`convert_to_symmetry { bodies <bodies>, type <type>, tolerance <rmsd> }`_
* **`bodies`** [`string`]: The bodies to decompose. Options:  
  i. single body: The body will automatically be split into the required number of subunits.  
  ii. multiple bodies: Each body is one subunit of the symmetry.  
* **`type`** [`string`]: The symmetry group to instantiate. Only point, cyclic, and polyhedral symmetries are supported.  
* `tolerance` [`float`]: The maximum RMSD in Ångström allowed for the conversion. Defaults to `5`.  

Convert the bodies into the given symmetry. The result will be a single body with the requested symmetry that best resembles the original structure. If the RMSD is larger than the tolerance, the element fails.  
The inline form `convert_to_symmetry <type>` applies to every loaded body.  

<details markdown="1">
<summary>Example</summary>

```
# a tetramer with one chain per subunit: use all four chains
load {
	pdb tetramer.pdb
	saxs measurement.dat
	split chain
}
convert_to_symmetry c4
```
```
# the same tetramer loaded as a single body: it is split into four subunits automatically
load {
	pdb tetramer.pdb
	saxs measurement.dat
}
convert_to_symmetry {
	bodies b1
	type c4
	tolerance 3
}
```

</details>

> [!TIP]
> This is the easiest way to optimize a symmetric assembly you already have a model of: `load` the full assembly, `convert_to_symmetry c4`, and optimize the symmetry parameters.

#### select
_`select <strategy>`_ or _`select { body <strategy>, mask <mask> }`_  

Specify how to select the bodies to transform.  
* **`strategy`** [`string`]: The chosen strategy.  
  i. `random_body`: Select a random body to transform. This is the default.  
  ii. `random_constraint`: Select a random constraint to transform from.  
  iii. `sequential_body`: Select each body in sequential order.  
  iv. `sequential_constraint`: Select each constraint in sequential order.  
  v. `random_symmetry`, `sequential_symmetry`: As `random_body` and `sequential_body`, but only the symmetry parameters are transformed. Inline form only.  
  vi. `<body>`: Always select this body, and transform both its position and its symmetries. Inline form only.  
  vii. `<symmetry>`: Always select this symmetry (e.g. `b1s1`), and transform only its parameters. Inline form only. 
* `mask` [`string`]: Which parts of the selected body are transformed in each step. Block form only.  
  i. `all`: Everything. This is the default.  
  ii. `real`: Only the position of the body itself.  
  iii. `symmetry`: Only the symmetry parameters.  
  iv. `symmetry_translation`: Only the symmetry translations.  
  v. `symmetry_axis`: Only the symmetry orientations.  
  vi. `sequential`: Alternate between `real` and `symmetry` steps.  
  vii. `random`: Pick `real` or `symmetry` at random each step.  
  viii. `sequential_real`, `sequential_symmetry`: Alternate between `all` and `real`, or `all` and `symmetry` steps, respectively. 

<details markdown="1">
<summary>Example</summary>

```
# move a random constraint, and everything attached to it
select random_constraint

# only optimize the first symmetry of b1
select b1s1

# visit the bodies in order, alternating between moving the body and its symmetries
select {
	body sequential_body
	mask sequential
}
```

</details>

#### transform
_`transform <strategy>`_  

Specify how to apply the transformation to the bodies.  
* **`strategy`** [`string`]: The chosen strategy.  
  i. `rigid` (or `rigid_transform`): All bodies connected to the chosen body will be transformed as well. This is the default.  
  ii. `single` (or `single_transform`): Only the chosen body will be transformed. This is likely to violate constraints on the transformed body with larger transformation amplitudes. 

> [!NOTE]
> Typically you want to combine the `single` strategy with smaller transformations, or limit it to only rotations.

#### on_improvement
_`on_improvement`_

Open a new [scope](#scopes) which will only be run if a better conformation (lower chi2) was found this iteration. This element must be placed directly inside an [`optimize_once`](#optimize_once) scope. 
Remember to terminate the scope with an `end` statement. 

> [!NOTE]
> This is primarily useful for saving a history of the optimization using `save` statements. 

---

#### every
_`every <N>`_  

Open a new [scope](#scopes) which will run once every `N` iterations.  

* **`N`** [`int`]: The number of activations required before the contained scope is run. 

Remember to terminate the scope with an `end` statement. 

> [!NOTE]
> This is useful for keeping track of the optimization progress without being overwhelmed. You can combine this with e.g. the `save` element to regularly see the optimization progress.

#### print
_`print <message>`_, _`print <color> <message>`_, or _`print { message <message>, color <color> }`_

Print a message to the terminal. 

* **`message`** [`string`]: The message to be printed.
* `color` [`string`]: The color of the text. Most basic colors are available; see [this link](https://github.com/AUSAXS/AUSAXS/blob/7e46a070c1fe2c2a9f2afa59013120faa1243943/include/core/utility/ConsoleColor.h#L15) for a list. 

Several runtime parameters can be printed using special keywords:  
i. `{iteration}`: The current iteration number.  
ii. `{iterations_total}`: The total iteration number.  
iii. `{chi2}`: The current reduced $\chi^2$ value.  
iv. `{chi2_best}`: The best reduced $\chi^2$ value found so far.  
v. `{chi2_penalty}`: The current penalty to the $\chi^2$.  
vi. `{chi2_no_penalty}`: The current $\chi^2$ without penalties.  
vii. `{body_names}`: The currently available body names.  

Braces are reserved for these keywords; any other `{...}` is an error. 

<details markdown="1">
<summary>Example</summary>

```
print {
	msg "{iteration}/{iterations_total}: Chi2 is {chi2}."
	color "red"
}
```

</details>

#### update
_`update structure`_  

Publish the current conformation to the GUI live preview. 

* **`structure`** [`string`]: The only supported target. 

Place this inside the optimization loop to update the preview as the run progresses. It does nothing if no GUI is connected, so it is safe to leave in scripts which are also run from the command line.

> [!NOTE]
> Rejected states are only available inside the [`optimize_once`](#optimize_once) [scope](#scopes). Placing this element there lets you watch every sampled conformation, while placing it outside the scope will only update once a new state is accepted.

### Advanced elements
These elements cover more specialised needs, and can safely be skipped when writing your first scripts.

#### rename  
_`rename <body> <name>`_

* **`body`** [`string`]: The body to be renamed. 
* **`name`** [`string`]: The new name. 

Rename a given body. The new name can be used to refer to this body in other elements.

#### copy  
_`copy <body> <name>`_

* **`body`** [`string`]: The body to be copied. 
* **`name`** [`string`]: The name of the new body. 

Add a copy of the given body, including any symmetries it has.

#### merge  
_`merge <body> <other bodies>`_

* **`body`** [`string`]: The primary body. 
* **`other bodies`** [`string`]: The bodies to be merged into the primary.

#### delete  
_`delete <bodies>`_

* **`bodies`** [`string`]: The bodies to be deleted. At least one body must remain.

#### split  
_`split <body> <splits>`_

* **`body`** [`string`]: The body to be split. 
* **`splits`** [`int`]: The list of residue ids to perform the split at. 

Split the given body into a number of new bodies, separated at the given residue ids. To split a structure as it is loaded, use the `split` argument of [`load`](#load) instead. 

---

#### relative_hydration
_`relative_hydration <body> <level>`_

* **`body`** [`string`]: The body to change. 
* **`level`** [`string`]: The amount of hydration relative to the other bodies. Options: `min` (×0.25), `low` (×0.5), `normal` (×1), `high` (×1.5), `max` (×1.75). 

Change the amount of hydration generated around a body, relative to the other bodies. Repeat the element to change several bodies. 

---

#### overlap_strength
_`overlap_strength <scaling> <distance>`_

* `scaling` [`float`]: Multiply the strength of the overlap penalty by this factor. 
* `distance` [`float`]: Only penalize overlaps closer than this distance in Ångström. 

Bodies are kept from overlapping by a penalty on short interatomic distances. By default its weight falls off as $e^{-5r}$; with this element it is scaled by `scaling`. If a `distance` $d$ is given, the weight is instead `scaling` $\cdot ((d-r)/d)^2$ for $r < d$, and zero beyond it.

#### settings
_`settings <setting> <value>`_

* **`setting`** [`string`]: The name of the setting, as written in a settings file. 
* **`value`** [`string`]: The new value. 

Change a program setting from within the script. Use `ausaxs rigidbody config --save` to see the available settings.

Set the seed of the random number generator. 

* **`seed`** [`int`]: The seed.
